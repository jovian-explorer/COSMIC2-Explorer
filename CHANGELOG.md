# Changelog

## Unreleased

### Updates and releases

- **One-folder build on Windows and Linux** (`COSMIC2-Explorer/COSMIC2-Explorer.exe` beside `_internal/`, as the release archive's folder already was). The one-file build unpacked itself (240 MB) into a new `%TEMP%\_MEI*` folder at every start and left it there whenever the app was killed (Task Manager, `taskkill /F`, a crash): the 2026-10-02 one-file build, hard-killed with `taskkill /F /T` after it answered, left its 240 MB folder behind. The one-folder build runs in place and writes nothing to `%TEMP%` (started in about a second, nothing in `%TEMP%` while running or after the same kill). The automatic update is unchanged: it already replaces the whole installation folder, and the executable keeps its path in it. `scripts/build_exe.py --archive` packs the whole folder; the Explorer launch test now points at `dist/COSMIC2-Explorer/COSMIC2-Explorer.exe` and checks that its six hard-killed launches leave no `_MEI*` folder (none did).
- **"You were N releases behind"** in the after-update panel, when an update skipped releases: the release notes shown are only the newest release's, so the panel adds how many releases came out since the installed build (counted from the repository's tags, which stay when old releases are deleted; from the release list if the tags cannot be read) and links GitHub's comparison of the old and new tags, or `CHANGELOG.md` when either tag is unknown. Tested with a fake GitHub (an update from build.1 to build.5 with only build.4 and build.5 still released: 4 behind, compare link; a missing tag or a failed tags request falls back to the CHANGELOG and never blocks the update) and in the browser; the compare URL form was checked read-only against the real repository.
- **Release policy in the release workflow**: after a successful publish, every release except the two newest is deleted with `gh release delete` (no `--cleanup-tag`, so all tags stay); drafts are neither counted nor deleted. Checked by running the step locally with a stand-in `gh` on five releases (the three oldest deleted, no tag clean-up, nothing deleted when only two exist); nothing was published.
- The automatic update always installs the newest published release (the highest tag among non-draft releases), never the next one after the installed build, and does not need the installed build's own release to still exist; a test covers an installed build three releases behind whose release is gone, with only the two newest listed (newest first) and a newer draft (ignored).
- **Worker processes end with the app.** A server or app killed outright (Task Manager, a crash) left its analysis workers running for good; in a one-file build each worker is a copy of the executable, so they also kept it locked and an automatic update could not move the installation aside. Each worker now waits on its parent's process handle and exits when the parent does: after a hard kill of a real server, all of its workers were gone within 2 s (7 of 9 kept running before).
- **Settings survive any version change, and what changed is shown once.** Every setting now has its allowed values (`config.SETTING_RULES`), checked when settings.json is read and when a value is saved (`POST /api/settings` answers 422 for a value out of range; it used to save any font size or theme name). A stored value this version cannot use (an option it does not have, a value outside its present range) is no longer dropped: the default stands in while the app runs and the stored entry is written back to settings.json unchanged. After an update, or when another version wrote settings.json, a panel opens once with what is new in the release (its notes, after an automatic update), the new options with their defaults, options whose allowed values or default changed, stored values that are not allowed now, and options no longer used, with the stored values filled in and editable (new module `settings_migration.py`, `GET /api/settings/changes`, `POST /api/settings/changes/ack`). Closing it changes nothing (settings.json is not even rewritten); the schema the user saw, and the stored values this version cannot use that were shown, are kept in `settings_seen.json`, so the panel is not shown again for them, while an option a later version drops is still reported by that version. Checked end to end: an older build (with an extra option, a wider DPI range and another default font size) updated itself to a newer one, and the panel listed exactly the new, removed and changed options and the release notes, with settings.json byte for byte unchanged. The stored `user_agent` is ignored on reading (it named the version that wrote it).
- **Weekly automatic update** (new module `autoupdate.py`, **Settings > Updates**, on by default, with **Check now**). A published build asks the GitHub releases API of jovian-explorer/COSMIC2-Explorer, anonymously as it will for everyone once the repository is public (a `GITHUB_TOKEN`/`GH_TOKEN` or a logged-in `gh` is used when present, and only towards api.github.com); releases are ordered by tag and pre-releases count. The newest build's archive for this platform is downloaded into the data folder's `updates/`, checked against its size and the SHA-256 digest GitHub lists (or the release's `SHA256SUMS.txt`; an archive with neither is not installed), unpacked beside the installation, and installed at the next start: the app exits, a script waits for it, renames the folder to `.previous`, moves the new one in and starts it with the same arguments; the new build then removes the old one. Only a folder holding the release's `INSTALL_FOLDER.json` is replaced, never one holding the data folder, and copies run from source or unstamped builds never update. A release whose archive for this platform is not uploaded yet is looked at again within the hour. `COSMIC2_UPDATE_API_URL` points the updater at another server (tests). Endpoints `GET /api/update/status`, `POST /api/update/check`.
- The automatic update starts the new build as an independent program (`PYINSTALLER_RESET_ENVIRONMENT=1`, the old build's `_PYI_*` variables removed). Inherited from the old one-file build, those variables made the new build's launcher take itself for a child of the old build, whose unpack folder was gone, and exit at once: the swap succeeded but the app did not reopen (found by the end-to-end test with two real builds).
- **Release archives for the automatic update.** `scripts/build_exe.py --archive` now packs one `COSMIC2-Explorer/` folder holding the app and `INSTALL_FOLDER.json` (the archive used to hold the bare executable), and `--tag v<version>[-build.<n>]` stamps the build with its release tag (checked against the version in `pyproject.toml`) in `src/cosmic2/_build.py`, which is removed after the build. The release workflow builds every pushed tag for Windows (x64), macOS (arm64) and Linux (x64), checks that each platform has exactly one archive named `COSMIC2-Explorer-<version>-<os>-<arch>.zip` (`.tar.gz` on Linux), adds `SHA256SUMS.txt`, and writes the release notes from the commits since the previous tag. A manual run builds unstamped archives and publishes nothing.

### Documentation and references

- The gravity-wave help and the diagnostic's text say that wetPf2's temperature follows its ECMWF first guess where the observation weighs little: on 187 COSMIC-2 occultations of 2026-09-27, wetPf2 minus ECMWF temperature had a standard deviation of 0.9-1.0 K from 20 to 30 km and 1.4-2.0 K at 35-40 km, against 1.6-2.7 K and 3.8-4.2 K for atmPrf. Its waves are not an independent measurement above about 30 km; atmPrf is the product for gravity waves.
- IVM `ap_pot` is labelled as its file names it, the aperture-plane potential (it was called the spacecraft potential, which the file does not say).
- The ivmL2m description promised the 3-component ion drift. In all nine complete files checked (every satellite on 2026-07-19 and 2026-09-27) the drift fields are missing values throughout, and C2E5 of 2026-09-27 also has no temperature or composition: UCAR masks ivmL2m fields not yet validated (Space Weather Data Release 4). The bundled file is byte-for-byte the archive's current one, so this is not an old copy. The product text and README now say so.
- ionPrf `hscale` was kept as `scale_height_km`, as if it were the profile's topside scale height. CDAAC's ionPrf format defines it as the "Scale height at orbit altitude (estimated and used only for icalib = 0)", and the files bear that out (filled in all 215 files with icalib = 0 of 2026-09-18, -999 in all 475 with icalib = 1). It is now `scale_height_at_orbit_km`, and the app's own topside scale height (the e-folding height of the density 50-150 km above the peak) says it is a different quantity. Profiles already indexed are updated when this version first starts.
- IVM drift texts follow the files: `iv_mer` was described as the north-south plasma speed, but the file defines it as the meridional drift positive upward (perpendicular to the field in the magnetic meridian, vertical at the magnetic equator); `iv_par` is positive northward along the field and `iv_zon` positive eastward. atmPrf `Azim` is the azimuth of the occultation plane (its long_name), not the direction a ray travelled.
- atmPrf `Imp_height_corr` was described as the corrected impact height and offered as a height coordinate. The file calls it the "Impact height correction for oblateness", and its values are a few metres (-3.8 to 0.6 m on the bundled profile): it is the correction, not a height. The variable text says so and it is no longer marked as a height axis.
- The guide and README said 8 bundled example granules of 5 products; the app ships and loads 12 of 7 (with the ECMWF and NCEP profiles). The help's list of fields interpolated in log space now names all of them (vapour pressure, specific humidity, refractivity and bending angle were missing).
- The rapid stream text said the ionosphere products are there; CDAAC's rapid level2 holds scnLv2 and ivmL2m, while ionPrf is in the provisional stream. The stream text and the guide now say so.
- The postProc stream was described as the final reprocessing to use for climate work, published weeks to months after observation. On CDAAC, COSMIC-2's postProc holds only in-situ IVM files (ivmL2m, 2019-08-01 to 2022-05-31, and ivmL2b/ivmLv2 in 2019-2020) and podTc2 of 2020: no atmPrf, wetPf2 or ionPrf. The stream text, the guide and the README now say so.
- Every citation with a DOI (35) was checked against its registry record (Crossref, DataCite): one was wrong. Bean and Dutton's *Radio Meteorology* was cited as the 1968 Dover edition, but its DOI (10.6028/NBS.MONO.92) is the 1966 National Bureau of Standards Monograph 92; the reference now matches the record.
- **"CDAAC Archive" links open.** The product and variable cards linked folders such as `.../cosmic2/nrt/level2/atmPrf/`, which do not exist (404): CDAAC keeps each day's tarballs in `<stream>/<level>/YYYY/DDD/`. The links now open the stream's level folder, and podTc2 and leoOrb point at level1b, where they are (podTc2 was listed under level2). An opt-in network test opens every link.
- The L1 and L2 bending-angle texts and the ionospheric-combination help gave GPS frequencies only (1575.42 and 1227.60 MHz). COSMIC-2 also tracks Galileo on E1 and E5a (1176.45 MHz; atmPrf `freq2 = L5Q`) and GLONASS on its own channels near 1602 and 1246 MHz; the texts now say so.
- README: the notes on the science say where scintillation files are placed and that they exist only for scintillating occultations; the list of what the tests check names the boundary-layer and scintillation-geometry tests.
- **Scintillation (S4) texts match the files.** The S4 and sigma-phi descriptions said the indices come from 1-second windows; every scnLv2 file says `calculation_time_interval = 10` with samples 1 s apart (602 files of 2025-12-21 and 2026-06-19), and the COSMIC-2 Space Weather Data Release 5 (UCAR, 2022) gives 10 s sliding windows of 50 Hz (GPS) or 100 Hz (GLONASS) data, output every second. S4 is also the normalized standard deviation of the intensity, not its variance. The product description now says that scnLv2 files exist only for occultations in which the receiver's own S4 passed a set threshold (same document), so averages describe scintillating occultations, not all of them. The thresholds quoted in the texts ("> 0.3 = strong turbulence", "above 0.4 means strong turbulence") disagreed with each other and with the scintillation class the app assigns (below 0.2 quiet, 0.2-0.4 moderate, 0.4-0.7 strong, 0.7 or more severe); they now quote the class. A test ties the texts to the bundled files and to the class thresholds.
- **Ducting: the texts say what a retrieved profile can and cannot show.** The refractivity-gradient entry of the Variables catalogue, the "Steepest refractivity gradient" diagnostic, the tutorial and the README presented ducting as something the app finds in the retrieved profiles ("values below -157 cause radio ducting"; "ducting layers"). Refractivity retrieved by Abel inversion never reaches the critical gradient: under a duct it is biased low instead (Sokolovskiy 2003; Xie et al. 2012), and on 952 COSMIC-2 and PAZ atmPrf of 2026 the app's own test found no duct while ECMWF diagnosed 183. The texts now say so and point to the weather-model card's ducting views, which the tutorial, help and README describe.
- Tutorial, README and the product catalogue describe the comparison cards as they now work: bending angle against ECMWF by impact height (missing from the tutorial and README), CDAAC's tropopause values with atmPrf only, the mission comparison's three estimates (collocated, less ECMWF's difference, through ECMWF over the common latitudes) and the satellite filter's "COSMIC-2, all satellites"; echPrf is also the first guess of the wetPf2 1D-Var of the same occultation and carries the model's ducting diagnostics (`ductid`, `zsr`, `dzsr`, `dndz`, `dzbot`, read in 2026 files of both missions).
- Help: three sections for the Statistics cards added since the last help update, checked against the code and the files: the tropopause and cold point by latitude (the WMO test as coded, CDAAC's `trhwmo`/`trtwmo` with atmPrf only, polar bands only from PAZ or KOMPSAT-5); the weather models (echPrf about 135 levels from the two fields its `Model_File_1/2` attributes name, avnPrf about 50; wetPf2's first guess is its echPrf; the impact height $a = n(R_c + z) - R_c$ of the model bending angles; the three-cornered hat and how correlated errors bias it); and the other missions (streams, the satellite filter, the three estimates and the 14-day result).
- Weather-model caption, temperature: wetPf2's 1D-Var first guess is the very ECMWF profile it is compared with (every good wetPf2 file names its same-stamp echPrf in the attribute `fgsPrf`: 1388 of 1388 COSMIC-2 and 880 of 880 PAZ files sampled from 14 days of 2026), so RO minus ECMWF temperature is the retrieval's departure from its own first guess at every height. The caption said only that the background was "a model forecast" and that the two were dependent "in the troposphere".
- **COSMIC-2 minus PAZ at 28-30 km explained in the mission caption.** The +0.45 K at 28-30.5 km on the first 108 pairs (two days) was looked into with 14 whole days of 2026 (72143 COSMIC-2 and 2673 PAZ wetPf2 profiles with their echPrf): with 817 pairs the difference is within about 0.1 K from 2 to 27 km and +0.19 to +0.28 K at 28-30 km collocated, +0.13 to +0.21 K minus ECMWF's difference (+0.17 K of the first 0.45 K was a difference ECMWF itself sees between the paired places and times) and +0.05 to +0.12 K through ECMWF over the common latitudes. It is the same for COSMIC-2's GPS, GLONASS and Galileo occultations and is already in wetPf2's dry temperature (before the 1D-Var); tighter (150 km, 1.5 h; 157 pairs) and wider (500 km, 6 h; 1419 pairs) windows agree within their intervals. Not a bug: a small real difference between the two missions' CDAAC profiles where RO records are known to diverge more (Steiner et al. 2020, doi:10.5194/amt-13-2547-2020: differences smallest from 8 to 25 km). The caption gives these numbers when PAZ temperature is compared. The collocation weights were checked in Rieckh et al. (2021), appendix A (0.75 dt / 3 h + 0.25 d / 300 km).
- **References and DOIs corrected** in the Variables catalogue, the product descriptions and the tutorial. 23 variables cited `10.1029/97RG02808`, which does not exist; others linked to unrelated papers (the ivmL2m ion density to a Mars 2020 overview, electron density to an Arctic Ocean study, S4/sigma-phi to an HF propagation correction). Every DOI the app shows has now been resolved at doi.org and its first author checked (Kursinski et al. 1997 is `10.1029/97JD01569`; COSMIC-2 products cite Schreiner et al. 2020, GRL; the IVM cites Heelis et al. 2017; and so on). Where no DOI exists (WGS-84, US Standard Atmosphere, textbooks without one) the reference text stays and the DOI is left empty. `tests/test_references.py` keeps the list honest and re-resolves it with `COSMIC2_NETWORK_TESTS=1`.
- Variable descriptions say what the app does: relative humidity is CDAAC's value (it is not computed here with Goff-Gratch); the refractivity gradient is smoothed over 5 levels; scale height uses constant g0; dry temperature equals the real temperature only in dry air, above about 8-10 km in the tropics.
- **Help, About, tutorial and product descriptions checked against the code and the data**, and corrected where they promised what the app does not do: there are no 5- or 10-degree latitude bands or hourly local-time groups (the groups are the fixed latitude bands, hemisphere, day/night, date, product and satellite); COSMIC-2 tracks GPS and GLONASS, not Galileo; it samples about 45 S to 45 N, not 30 S to 30 N; ionPrf profiles end at the satellite's orbit (about 550-580 km), not 800 km; atmPrf files reach 80 km, not 130 km; wetPf2 levels are 50 m apart up to 20 km and 100 m above, not a uniform 100 m; potential temperature uses 1000 hPa (the help said 1013.25 hPa) and density, scale height and N^2 use constant g0 (the help showed g(z)). The tutorial now says which retrieval steps CDAAC performs and which diagnostics the app computes; the outlier and smoothing options are described as they are implemented (whole-profile 3-sigma, 3 MAD, 3 IQR, 5th-95th percentile, 5-level windows) and as display-only; figures are no longer said to embed provenance. Citations are "suggested", not "mandatory", the software no longer claims to "validate" data it only analyses, and citation blocks quote the running version.
- README: the app no longer claims "comparative planetary atmospheric profiles" (it has no planetary data or comparison) or to be "production-quality"; the feature list, product table and stream latencies match the app and the files (see the corrections above); it says that the retrievals are CDAAC's and the diagnostics the app's, and that figure files carry no provenance.
- The tutorial describes the new Statistics tab (sampling and quality, sections, diagnostic maps, radiosonde comparison) with a button to open it.
- DATA_POLICY.md: no account is needed for CDAAC (it said registration through UCAR credentials); the UCAR data DOI is `10.5065/T353-C093` (it gave a DOI that does not resolve); the streams listed are the ones the app reads; no Parquet files are written. pandas and Requests are added to the third-party licences.
- The data terms no longer call UCAR CDAAC data "public domain": UCAR publishes no licence text, and asks for a citation of doi:10.5065/T353-C093. The NCEI, TASA, NASA CDDIS and ISRO ISSDC portals are labelled as references the app does not download from.

### New science features

- **Boundary-layer tops against radiosondes.** With atmPrf, the radiosonde comparison (Statistics) now also finds the boundary-layer top in both profiles of every pair, the same way (help, section O) and on the same geopotential heights, and plots occultation against sonde with the mean, median and standard deviation of the difference, the correlation and the share within 0.5 km, beside Guo et al.'s (2011) and this app's 2026 check; the table lists both tops and the CSV adds `ro_pbl_km` and `sonde_pbl_km`. With wetPf2 it says why there are none (its refractivity is the 1D-Var analysis). Tested with a sonde built from an atmPrf's own pressure and temperature (the two tops coincide; a profile stopping above 0.5 km has none on either side); in the browser on 15216 atmPrf of May-June 2026 (200 km, 3 h: 147 pairs, 38 with a top in both, mean -0.08 km, standard deviation 0.95 km, correlation 0.32), no console errors at 1024 and 1366 px.
- **Refractivity bias under ducting** (Statistics tab, weather-model card, two new views; `kind` `ducting` and `ducting_rel` of `POST /api/compare/models`, `nwp.ducting_differences`): RO (atmPrf) minus ECMWF refractivity for the occultations where ECMWF diagnoses a duct (echPrf `ductid` 1-3) and where it does not, and around the duct, by height relative to the centre of ECMWF's super-refraction layer (echPrf `zsr`). On 952 COSMIC-2 and PAZ occultations of 2026-06-20 and 09-30, ECMWF diagnosed a duct at 183 (19 %): there RO minus ECMWF is -4.2 % at 1 km (-1.4 % without a duct) and -8.4 % [-9.2, -7.6] 0.2 km below the duct centre, back to +0.3 % 0.2 km above it, as published: a negative refractivity bias below ducts of up to about 10 % (Sokolovskiy 2003, doi:10.1029/2002RS002728), mostly below about 2 km (Feng et al. 2020, doi:10.1175/JTECH-D-19-0206.1). The retrieved RO profile cannot show the duct itself: its steepest gradient below 5 km was never below -110 N-units/km on these 952 profiles (median -73, 5th percentile -95 for COSMIC-2), as Xie et al. (2012, doi:10.5194/acp-12-903-2012) report, so the app's own test on retrieved refractivity (dN/dz at or below -157) found no duct at all. Choosing either view sets the grid to 0-6 km by 0.1 km.
- **Collocated mission pairs corrected with ECMWF** (Statistics tab, mission card; `collocated.corrected` in `POST /api/compare/missions`): each COSMIC-2 / PAZ (or KOMPSAT-5) pair's difference less the difference between the ECMWF profiles (echPrf) of its two occultations, which removes the part of the mismatch in place and time that the model resolves (the sampling correction of Gilpin et al. 2018, doi:10.5194/amt-11-2567-2018). On 14 whole days of 2026 (817 PAZ pairs) the spread of the temperature pair differences falls from 1.16 to 0.74 K at 10 km and from 1.56 to 1.30 K at 29.5 km, and the 28-31 km difference goes from +0.19..+0.28 K to +0.02..+0.21 K (95 % interval at 29.5 km +0.12..+0.30 K); same numbers from an independent script. Shown as a third line with its 95 % interval.
- **COSMIC-2 against PAZ and KOMPSAT-5** (Statistics tab, `POST /api/compare/missions`, new module `missions.py`), two independent ways: collocated pairs (each profile of the other mission paired one-to-one with the COSMIC-2 profile nearest in 0.75 |dt|/3 h + 0.25 d/300 km within 300 km and 3 h, the weights of Rieckh et al. 2021) and the double difference mean(COSMIC-2 - ECMWF) - mean(other - ECMWF) through each occultation's echPrf, which needs no collocation. Temperature (wetPf2), 1D-Var refractivity (wetPf2) or observed refractivity (atmPrf), by height, with spread and 95 % intervals. On whole days of 2026-06-20 and 2026-09-30 (10 438 COSMIC-2, 382 PAZ and 92 KOMPSAT-5 good wetPf2): 108 COSMIC-2/PAZ pairs (median 182 km, 0.96 h apart) give a temperature difference within 0.23 K from 2 to 25 km (up to +0.45 K at 28-30.5 km, the only levels whose 95 % interval excludes zero) and a 1D-Var refractivity difference within 0.25 % above 5 km but +0.7 % at 3-4 km (9 of 67 levels with intervals excluding zero); through ECMWF within 0.12 K and 0.12 % above 5 km. The two estimates agree within their combined uncertainty at 91 % of the levels from 2 to 35 km for PAZ and 88-94 % for KOMPSAT-5 (18 pairs only). Missions are told apart by the satellite code in the file names, so imported files count too.
- **Tropopause and cold point by latitude with 95 % intervals** (Statistics tab, `POST /api/climatology/tropopause`): for each latitude band the mean, 95 % confidence interval of the mean, median, spread and count of the WMO tropopause height and temperature and of the cold point, from the good atmPrf or wetPf2 profiles of the search, and for atmPrf CDAAC's own values from the same files beside them. On the 293 good atmPrf of 2026-06-20 between 20 S and 20 N the tropopause is at 16.65 km and 194.0 K (wetPf2: 16.64 km, 194.2 K), within the 16-17 km and the July mean of 195 K that Rieckh et al. (2014, Atmos. Meas. Tech., doi:10.5194/amt-7-3947-2014) report for 2001-2013; at 40-50 S, in winter, 214.7 K against their 215 K for the winter hemisphere. The band means agree with CDAAC's own `trhwmo`/`trtwmo` within 0.06 km and 0.1 K except at 20-30 S (0.15-0.2 km). The cold point is the coldest level between 10 and 30 km; the caption says it is a tropopause only in the tropics (at 40-50 S in winter it is at 24-26 km).
- **Bending angle against ECMWF, by impact height** (the quantity weather centres assimilate; Statistics tab, weather-model card). echPrf carries ECMWF's simulated bending angle on its own levels; the file does not say at which impact height, so both readings were tested on 300 real pairs: placed at the impact height of their tangent points, n (Rc + z) - Rc with the occultation's radius of curvature Rc (the relation atmPrf's own Impact_height follows to the metre), RO minus ECMWF is within 0.15 % from 10 to 35 km, while taking MSL_alt as the impact height gives offsets of +0.3 % to +23 %. On the 570 good atmPrf of the 2026 sample: mean within 0.2 % from 8 to 35 km of impact height, standard deviation 1.0-2.2 % with its peak at 18 km (the tropical tropopause, where Rieckh et al. 2021 also find COSMIC-2's bending-angle error largest, about 2 %), 4.7 % at 8 km and 12-16 % below 5 km. CDAAC's own `Bend_ang_stdv` ("bending angle uncertainty") is 0.15-0.3 % at 10-15 km, far below this scatter, so it is not used as an error estimate.
- **Radio occultation against the ECMWF and NCEP profiles of the same occultations, and error estimates by the three-cornered hat** (Statistics tab, `POST /api/compare/models`, new module `nwp.py`). RO minus each model by height (refractivity from atmPrf in percent, temperature from wetPf2 in K) with spread and 95 % confidence interval; and, for refractivity, the error variance of each of RO, ECMWF and NCEP from the variances of their pairwise differences, sigma_X^2 = (var(X-Y) + var(X-Z) - var(Y-Z)) / 2 (Rieckh et al. 2021, J. Atmos. Oceanic Technol., doi:10.1175/JTECH-D-20-0209.1), with 95 % intervals from 200 bootstrap resamples of the occultations. The estimator is checked on synthetic data with known independent errors, and its documented bias when errors are correlated (both models assimilate COSMIC-2 and share most other observations) is checked too. On the 570 good atmPrf of 2026-06-20 and 2026-09-30 with both model profiles: RO refractivity error variance 10.9 %^2 [9.0, 13.2] at 1 km, 7.1 [5.7, 8.4] at 2 km, 1.3 at 6 km and 0.19-0.28 %^2 from 10 to 25 km, rising to 0.55 at 30 km, in the range Rieckh et al. (2021, their Fig. 3) report for COSMIC-2 in October-November 2019 (a peak of about 8-9 %^2 near 2 km, about 0.1-0.4 %^2 from 10 to 30 km). RO minus ECMWF refractivity is -2.9 % at 0.5 km (the near-surface negative bias also seen against radiosondes) and within 0.15 % from 5 to 30 km; wetPf2 minus ECMWF temperature is within 0.4 K (standard deviation 0.5-1.2 K). RO minus NCEP refractivity rises to +0.7 % around 17-18 km only between NCEP's 100 and 70 hPa levels (2 km apart at the tropical cold point): at those levels it is +0.2-0.3 %, so the bump is interpolation, and the caption says so.
- **ECMWF and NCEP model profiles at each occultation (echPrf, avnPrf) can be downloaded, read and plotted.** CDAAC publishes, for every occultation, the ECMWF fields colocated along its path (temperature, pressure, water vapour pressure, refractivity and simulated bending angle, about 135 levels) and the NCEP fields interpolated the same way (about 50 levels), named with the same file stamp as the atmPrf. They had no reader, and the catalogue described avnPrf as a retrieved profile (its own history attribute says it is converted from GRIB model fields). A whole day is small (echPrf 54-69 MB, avnPrf 21-27 MB for 4947-6327 occultations), and both were downloaded for 2026-06-20 and 2026-09-30 through the Get data tab. The model files' own temperature, pressure and vapour pressure give their refractivity through the Smith-Weintraub formula within 1 % (test). The two bundled occultations now include their echPrf and avnPrf.
- **Optional outlier screen** for the Compare averages, their exported figure and the latitude-height sections (`screen_k`). Within each group (or latitude band), a profile is left out when it is more than k robust standard deviations (1.4826 times the median absolute deviation; k = 5 by default) from the group's median at consecutive levels at least 1 km apart; a single spiky level does not count, and groups or levels with fewer than 10 profiles are not screened. The caption says how many profiles were left out. It is a statistical screen, not a quality check, so it is off by default. On the real 2026 data (5 latitude bands) it leaves out 7 of 568 good wetPf2 temperature profiles and 8 of 570 atmPrf refractivity profiles; the equatorial wetPf2 temperatures have a robust spread of 1.0-1.2 K at 5-15 km, and a real profile with 5 K added over 5-15 km is caught 29 times in 40, with 8 K 40 times in 40, while a 30 K spike at one level never is. One of the profiles it leaves out starts at 4 km (high ground) and is 7.7 K warmer than the band median at 8.5 km: a real but unusual profile.
- **atmPrf against wetPf2 for the same occultations** (Statistics tab, `POST /api/compare/products`). Each wetPf2 file names the atmPrf it was retrieved from, so the two are paired exactly, whichever product the search holds. Four comparisons by height, with mean, median, spread, standard error and 95 % confidence interval: refractivity, atmPrf (observed) minus wetPf2 (1D-Var analysis), in percent; dry temperature and dry pressure of the two files (both carry the dry retrieval); and the moisture effect, wetPf2 temperature minus dry temperature. On the 549 real 2026 pairs: refractivity -0.65 % at 0.5 km, -0.48 % at 1 km, within 0.05 % from 3 to 30 km; dry temperature within 0.1 K from 3 to 15 km; moisture effect 56 K at 0.5 km (median of all profiles; 58 K in the tropics), 12 K at 5 km, 1 K at 10 km, under 0.1 K above 14 km. Checked two ways: the moisture effect equals T - 77.6 P_dry / N, with N from the Smith-Weintraub formula of the wetPf2 state, within 1 % from 0.5 to 12 km; and the radiosonde comparison, run separately on the atmPrf and on the wetPf2 of the same occultations, gives the same sign and size of refractivity offset between them near the ground (-0.36 % at 0-1 km, -0.26 % at 1-2 km, 0.0 % at 3-4 km, on 23-26 sonde pairs).
- **Uncertainties in the climatologies.** The latitude-height section can show the standard error of each cell's mean (`sem` in `POST /api/climatology/section`), and the zonal means of the diagnostic map carry the 95 % confidence interval of the mean (`sem`, `ci95_lo`, `ci95_hi`; drawn as thick bars over the ± 1 standard deviation bars). Both treat the profiles as independent and leave out sampling error. Checked on the 600 real 2026 wetPf2 profiles by splitting them at random into halves ten times: the section's cell means agree within 1.96 combined standard errors in 94.1 % of 2820 comparisons (normalised differences: standard deviation 1.03), the zonal-mean WMO tropopause heights in 92 % of 100 (1.05). The tropical (10 S - 10 N) tropopause comes out at 16.7 km with a 95 % interval of ± 0.11-0.12 km.
- **Uncertainty of the mean in composites.** Each Compare average now carries the standard error of the mean, s/sqrt(n), and the 95 % confidence interval of the mean from Student's t with n - 1 degrees of freedom at every level (`sem`, `ci95_lo`, `ci95_hi` in the composite response); the Compare tab and the exported composite figure can shade that interval instead of the spread. It treats the profiles as independent and leaves out sampling error, which the caption says. Checked against the t table (t(0.975, 9) = 2.262), by simulation (the interval covers the true mean in 95.0 % of 20 000 Gaussian draws of six) and on the real data: splitting each day's 300 good wetPf2 profiles at random into two halves five times, the half-means differ by less than 1.96 combined standard errors at 94.4 % of 1200 band-levels (normalised differences: standard deviation 1.03). On 2026-06-20 the standard error of the equatorial (165 profiles) mean temperature is 0.07-0.2 K from 5 to 30 km.
- **Statistics tab: sampling, quality flags and penetration depth.** For the current Explore search (or the selection) it counts profiles by product, latitude and local solar time, lists how many CDAAC flagged as bad and with which `bad` code, and shows the penetration depth of good neutral profiles: the lowest retrieved level as a histogram with the cumulative fraction, its median by latitude, and the fraction reaching below 1 km above sea level and above the ground. The above-ground height uses the terrain height stored in the wetPf2 file retrieved from the same atmPrf. On the 600 atmPrf profiles of 2026-06-20 and 2026-09-30, 84.5 % of the 549 with a matching wetPf2 reach within 1 km of the ground, in line with the more than 80 % reported for COSMIC-2 by Schreiner et al. (2020); the lowest levels agree with CDAAC's `profile_bottom_km` to 0.2 mm. New endpoint `POST /api/stats/sampling`; it reads only the index, so it is instant.

- **Zonal-mean latitude-height sections** (Statistics tab, `POST /api/climatology/section`) of any quantity: mean, standard deviation or count of the profiles in each latitude band and height, or each band's departure in percent from the mean of all profiles at that height (for refractivity, the `N_anom_pct` the Variables catalogue described but nothing computed). The product follows the quantity (wetPf2 preferred for temperature); dry and moist temperature are refused rather than averaged together. On the real 2026 sample: wetPf2 cold point -79 C at 17 km at the equator and -57 C at 18.5 km at 45 N; refractivity 5-7 % above the mean at 2-5 km in the moist 0-10 N band; the ionPrf F2 peak densest near 15 N (the equatorial anomaly crest).

- **Gravity-wave potential energy: a second background filter and a documented transfer.** `analysis.gravity_wave_energy` takes `method="highpass"` (zero-phase 4th-order Butterworth, cut-off wavelength `cutoff_km`, 10 km by default, applied to the departure from a linear trend over the layer plus 5 km on each side) besides the default 4th-order polynomial, and any layer (`z_lo`, `z_hi`). Both are checked against a sine wave of known energy (`tests/test_gravity_waves.py`): the polynomial over 20-40 km recovers 98 % of the energy at 2 km wavelength, 90 % at 5 km and 75 % at 10 km; the high-pass 98-99 % at 2-5 km and under 1 % at 15 km. On the 570 good atmPrf profiles of 2026, the high-pass over 20-30 km gives a tropical (|lat| < 20) mean of 6.0 J/kg, within the 6-10 J/kg of Tsuda et al. (2000) for that layer; the per-profile diagnostic (polynomial, 20-40 km) is unchanged.

- **Maps and zonal means of any per-profile diagnostic** (Statistics tab, `POST /api/climatology/map`, coastlines from `GET /api/coastlines`): the mean in latitude-longitude cells and the zonal mean, median and spread by latitude band of gravity-wave energy, tropopause height, foF2, TEC, column water vapour and the rest. Gravity-wave energy is recomputed for the chosen layer and background filter. On the 570 good atmPrf profiles of 2026 (20-30 km, 10 km high-pass) the zonal mean peaks at 7.4 J/kg in 0-10 N and falls to 0.9-1.8 J/kg poleward of 30 degrees. The worker warm-up now also imports `scipy.signal`, which took 2 s on the first gravity-wave map.

- **Validation against radiosondes from NOAA IGRA v2** (Statistics tab, `POST /api/validation/radiosonde`, new module `radiosonde.py`). Each good atmPrf or wetPf2 profile is paired with the nearest IGRA sounding launched within a distance and time window (300 km, 3 h by default); the differences (occultation minus sonde) in temperature, refractivity (%) and specific humidity are compared on geopotential height and summarised as mean, median, standard deviation and count per height bin, with the list of pairs and an optional CSV export. Station files are fetched from NCEI only for stations near an occultation, cached (parsed soundings kept beside them, so a repeated comparison takes seconds), refreshed when an occultation is newer than the copy, and a station the archive lacks is not asked for again for a day. atmPrf heights are converted to geopotential height with Mahoney's (2001) normal gravity, within 2 m of wetPf2's own `gph`. On the 2026 sample, 45 wetPf2 profiles have a sonde: mean temperature differences within 0.5 K from 0 to 25 km (standard deviation 1-1.7 K), refractivity within 0.6 % from 3 to 30 km and 2.6 % low at 0-1 km, comparable with the 3-4 % near-surface negative bias Ho et al. (2020) found against RS41 sondes. A synthetic sonde built from a profile's own fields reproduces it to 0.02 K (`tests/test_radiosonde.py`).

### Science fixes (results change)

- Averages and latitude-height sections of fields derived from temperature (potential temperature and its gradient, lapse rate, N^2, buoyancy period, density, scale height, speed of sound) pooled atmPrf, where they come from the dry temperature and pressure, with wetPf2, where they come from the real ones, and counted occultations with both files twice. They are now separate groups ("Potential temperature (from dry temperature)"), and a section refuses the mix, as for `Temp` itself.
- The diagnostic map counted an occultation twice when both its atmPrf and its wetPf2 were selected (tropopause, cold point, gravity-wave energy are computed from both). Each occultation now counts once, by its wetPf2's value when it has one, else its atmPrf's (the boundary-layer top is atmPrf-only).
- The radiosonde comparison of "selected profiles only" pooled atmPrf and wetPf2 when both were selected, so the temperature differences mixed the dry temperature (tens of kelvin from the real one in the moist lower troposphere) with the real one, and counted occultations twice. The comparison now uses the product chosen on the card, and the API refuses a selection holding both unless a product is named.
- The tropopause table counted an occultation twice when both its atmPrf and its wetPf2 were selected, so its 95 % intervals, which take the profiles as independent, were too narrow by about a factor of 1.4. Each occultation now counts once, by its wetPf2 (moist, real temperature) when both are there; CDAAC's columns still come from the atmPrf files.
- The radiosonde comparison read a station's file only for the year of each occultation, so near New Year it missed soundings within the time window that IGRA files under the other year (an occultation at 23:30 UTC on 31 December and the 00 UTC sonde of 1 January). It now reads both years whenever the window crosses into the other one.
- **Averages never mix observations with weather-model profiles.** echPrf (ECMWF) and avnPrf (NCEP) use the observations' variable names (`Temp`, `Ref`, `Bend_ang`), so a Compare average or latitude-height section over a selection holding wetPf2 and echPrf, say, averaged the retrieved and the model temperature together. Such a selection is now split into separate groups ("Temperature" and "Temperature (ECMWF)"), and a section refuses it, as for dry and moist temperature.
- A scintillation file without the ray geometry (placed at CDAAC's `lat/lon_s4max_L1`) took its local time from `lct_s4max_L1`, which is not the local solar time there: 15.38 h at 164 E at 15:22 UTC on a bundled file, where it is 2.3 h, and likewise for `lct_start`/`lct_stop`. Its local time is now computed from the time and longitude, like every other product's.
- **Profile outlier filters test each level against its neighbours.** The sigma, MAD, IQR and percentile filters of the Profiles tab compared each value with the whole profile's values, which change with height by orders of magnitude: on a clean atmPrf, refractivity lost its lowest 20 km to the MAD filter (920 levels) and its lowest 2.5 km to the 3-sigma filter, pressure likewise. Each level is now tested against the 20 levels around it (of the logarithm when the quantity is positive), the MAD filter being a Hampel filter. On the bundled atmPrf, wetPf2 and ionPrf no level is removed, and a 20 % spike on a noisy synthetic profile is the only level removed by every filter. These filters change the plot only, never exports.
- **Local solar times of atmPrf and ionPrf are computed, not taken from the files.** atmPrf's `timloc` is the local time of the occultation's start cut to the whole minute in GPS time (exact on all 22 COSMIC-2 and PAZ atmPrf tested), so it was 0-60 s early and another 18 s off UTC; ionPrf's `edmaxlct` is the local time of `edmaxtime` read as UTC, 18 s late (all 200 tested). Both are now the mean local solar time of the profile's UTC time at its longitude, as for every other product, so the products of one occultation agree.
- Bending angles are interpolated in log space when profiles are put on a common grid (composites, sections, exports), like refractivity. They fall off with a scale height of about 6 km, and across the 2 km between echPrf levels above 30 km a straight line put them up to 1.3 % too high. The weather-model bending comparison already did this.
- **IVM ion densities of zero or below are missing values.** ivmL2m `ion_dens` is `orig_ion_density` rescaled to agree with TGRS TEC (FORMOSAT-7/COSMIC-2 Space Weather Data Release 4, UCAR 2021); the correction also subtracts about 7900 /cc, so where the raw density was lower it comes out negative (604 of the 84520 samples of the bundled day, down to -7900 /cc). These went into medians, maxima, plots and composites, and broke the log-space interpolation. They are now missing, their number is kept in the metadata (`n_nonpositive_ion_dens`), and the variable text says that the release validates densities above 8000 /cc. The `rpa_flag`, `dm_flag` and `sc_flag` values are not documented by UCAR or in the files, so they are not applied.
- **Times are UTC.** CDAAC's date and time attributes (year ... second in atmPrf, ionPrf, scnLv2, echPrf, avnPrf; `date` in wetPf2) are GPS time, which runs 18 s ahead of UTC since 2017: they equal the files' own GPS-second fields (atmPrf `start_time`, ionPrf `edmaxtime`) counted from 1980-01-06 without leap seconds, on every file checked, and in scnLv2 the Earth rotation angle the file gives (`gast1`) matches its first sample only when that time is taken 18 s earlier as UTC (0.4 s left, within the equation of the equinoxes). The app showed and used them as UTC; it now subtracts the leap seconds (14-18 s from 2006 on), so times, local solar times and radiosonde time differences are 18 s earlier than before. ivmL2m already gives UTC (`uts`) and is unchanged. The index is updated when this version first starts.
- **ionPrf TEC columns start at 80 km, like CDAAC's tec0.** On about 10 % of ionPrf the profile TEC was 4-13 % above the archive's `tec0`. The cause was the lower limit: the app integrated from the lowest level (often 30-50 km), where the densities are Abel-inversion residue (median peak 1e4 el/cm3 below 80 km, 1.3e5 at the 90th percentile, against under 1e3 in the real D region), while `tec0` starts at 80 km. Integrated from 80 km, 689 of the 690 ionPrf of 2026-09-18 agree with `tec0` within 0.5 % (435 before). The TEC below the peak starts at 80 km too.
- foF2 uses the plasma-frequency coefficient from the physical constants, 8.97866e-3 MHz per sqrt(el/cm3), instead of the rounded 8.98e-3, which put it 0.015 % high (about 1.4 kHz at 9.4 MHz).
- **ionPrf profiles whose archive peak is in the E region are placed at the F2 peak.** Each ionPrf is placed at CDAAC's density maximum (`edmaxlat`, `edmaxlon`, `edmaxlct`). On 5 of the 690 ionPrf of 2026-09-18 that maximum is at 40-93 km, and its tangent point lies 660-1600 km from that of the F2 peak, which is what the app reports as the profile's peak (hmF2 236-346 km). Those profiles are now placed at the tangent point of the largest density above 150 km, with the local solar time there; the others are unchanged. Profiles already indexed are updated when this version first starts.
- **atmPrf geoid undulation in metres.** The atmPrf metadata column `geoid_undulation_m` held `rgeoid` as the file gives it, in km (0.05091 for an occultation whose wetPf2 says 50.91 m; the same factor on all seven atmPrf/wetPf2 pairs checked), so it was 1000 times too small. Profiles already indexed are updated when this version first starts.
- **Setting or rising occultation is read correctly.** The app read atmPrf and wetPf2 `irs = -1` as setting, following the wetPf2 attribute text ("rising (=1) or setting (-1)"), so every COSMIC-2 atmPrf and wetPf2 had the wrong direction; and every ionPrf was called rising, because the reader looked for `setting = -1` while ionPrf says 1 for setting and 0 for rising. CDAAC's atmPrf format gives irs = +1 for setting, and the files agree: on 2026-09-16 each of the 2044 wetPf2 matched to the ionPrf of the same occultation (same satellite and GNSS, time within the ionPrf's) has `irs = 1` exactly when that ionPrf is setting (1268 setting, 776 rising, no exceptions), the ionPrf flags match their bottom and top times (all 690 ionPrf of 2026-09-18), and PAZ, which records setting occultations only (Padullés et al. 2020, doi:10.5194/amt-13-1299-2020), has `irs = 1` in every file that has it (171 of 187 wetPf2 of 2026-09-27). The sign was also checked on the geometry of each occultation: the satellite's direction of motion (from its position at consecutive occultations) against the direction it looks to the tangent point. Looking backwards means setting; every one of 168 PAZ atmPrf of 2026-09-27 looks backwards (irs = 1), and so does each KOMPSAT-5 atmPrf with irs = 1 (67 of 2026-09-26 and 27), while each of its 21 with irs = -1 looks forwards: KOMPSAT-5 records rising occultations too, and its labels follow irs. A file without the flag is now left unsaid instead of being called rising.
- **Boundary-layer top: a published method with its acceptance tests, from atmPrf only, checked against radiosondes.** The diagnostic took the steepest refractivity gradient anywhere below 6 km, with no test that a capping layer was there, and also used wetPf2's 1D-Var analysis refractivity. Against IGRA radiosondes put through the same steps (15216 COSMIC-2 atmPrf of 2026-05-20, 06-05 and 06-15; 621 pairs within 200 km and 3 h) it was 0.88 km too high with a spread of 1.71 km (correlation 0.16; 20 % within 0.5 km). It now follows Ao et al. (2012, doi:10.1029/2012JD017598): the centre of the 300 m window, on a 5 m grid, where N falls fastest, accepted only with the tests of Guo et al. (2011, doi:10.1175/2011JAS3612.1): the profile reaches 0.5 km above sea level, the top is below 3.5 km and N falls there by more than 50 N-units/km (otherwise the reason is given). On the same pairs: +0.08 km (median +0.01 km), spread 0.92 km, correlation 0.41, 48 % within 0.5 km, for the 185 pairs with a top in both (213 occultations and 421 sondes had one). Guo et al.'s own definition, the break point where the slope changes most, did slightly worse here (145 pairs, spread 1.05 km, correlation 0.24). Their comparison between 30 S and 30 N (0.04 km, 0.35 km, 0.82) is matched in the mean, not in the spread: the occultations' tops are much less sharp than the sondes' (median -73 against -108 N-units/km). wetPf2 no longer gets a top: on 952 occultations its tops differed from the atmPrf ones by more than 0.3 km in a third of the 236 cases where both had one; the diagnostic map takes atmPrf for it. Method and check in the help, section O.
- **Scintillation files (scnLv2) are placed where the ray grazed the ionosphere, not where the satellite was.** The app put each file at CDAAC's `lat_s4max_L1`/`lon_s4max_L1`, but in COSMIC-2 files those attributes (with `alt_s4max_L1`, about 570 km) are the satellite's own position at the S4 maximum: on 602 files of 2025-12-21 and 2026-06-19 they equal the satellite's latitude and longitude at that second, while the ray's tangent point was a median 1947 km away (10-90 %: 1236-2381 km). Maps, region searches and local times of scintillation now use the tangent point of the ray at the S4 maximum (the point of the straight satellite-to-transmitter line closest to the Earth, as RO scintillation studies locate it, e.g. Dymond 2023, doi:10.5281/zenodo.8084380), computed from the file's own satellite and transmitter positions, which are inertial and are turned Earth-fixed with the file's sidereal angle `gast1`. Checked on those 602 files: the satellite positions turned this way match the file's `lat`/`lon` within 0.0002/0.006 degrees at every second, and the tangent heights its `occheight` within 1 m; for the 279 of them whose occultation also has an ionPrf, the new position lies 8.4 km (median; at most 8.8 km) from CDAAC's own ionPrf tangent point at the same height. The archive values keep CDAAC's numbers as `satellite_lat/lon/alt_s4max_L1` and add `tangent_height_s4max_L1_km`. Files downloaded before this version keep their old position until **Rebuild index** (Get data, On this computer) is run.
- **COSMIC-2 against PAZ or KOMPSAT-5 through ECMWF uses the latitudes both missions cover.** The double difference mean(COSMIC-2 - ECMWF) - mean(other - ECMWF) took every profile of each mission, but COSMIC-2 reaches only about 45 degrees and PAZ the poles, and RO minus ECMWF changes with latitude. On 14 whole days of 2026 (72143 COSMIC-2 and 2673 PAZ wetPf2 profiles) the temperature difference at 5 and 10 km was +0.12 and +0.09 K with every profile and is +0.06 and +0.05 K over the common latitudes (44.7S to 44.6N, 1416 PAZ profiles), as with 10-degree strata weighted by PAZ (+0.07, +0.06 K). The caption names the latitude range.
- **Refractivity is interpolated in log space** when profiles are put on a common grid, like pressure and density. On the NCEP model profiles (avnPrf), whose levels are 2-3 km apart above 17 km, straight-line interpolation made refractivity 1.7-2.0 % too large between 20 and 35 km, which looked like a 2 % NCEP-ECMWF difference; at the files' own levels the two agree within 0.3 %, and after the fix the gridded difference is within 0.2 % from 5 to 40 km. On the dense RO profiles the change is below 0.003 % (atmPrf) and nil (wetPf2).
- **Vertical TEC below hmF2** now integrates the whole profile from its lowest level up to the F2 peak. It previously started at 150 km, dropping the E and lower F region (bundled ionPrf sample: 14.3 to 16.4 TECU).
- **TEC ignores negative electron densities**: ionPrf profiles often carry a negative bottomside (an Abel-inversion artefact, typically -4e4 el/cm3 below 100 km), which was integrated as it stood and removed TEC: on one real 2026-09-30 profile the column came out 0.4 TECU instead of 11.5. Negative densities now count as zero, as in CDAAC's own integral. A new whole-profile `vtec_profile_TECU` sits beside `vtec_below_peak_TECU` and is cross-checked against the archive in the Profiles diagnostics (median agreement 0.2 % over 119 profiles); both TEC values are shown in the diagnostics panel.
- The archive's ionPrf `tec0` was labelled "TEC below edmax". CDAAC defines it as the TEC integrated between the bottom and top of the profile, and `tec1` as the extrapolated TEC above the top; they are now `tec_profile_TECU` and `tec_above_top_TECU`.
- **E layer**: an electron-density maximum on the edge of the 90-150 km window is no longer reported as an E layer (the bundled sample showed a spurious "hmE" of 149.4 km, which is the F-region bottomside). An F2 maximum on the first or last level of a profile is flagged `peak_at_profile_edge` and not reported as found. hmF2/NmF2 refinement uses the exact parabola vertex for uneven level spacing.
- **Integrated water vapour**: when specific humidity had missing levels, the remaining humidities were paired with the first N pressures instead of the pressures at the same heights. Fixed; the lowest integrated level is reported as `column_water_vapour_bottom_km`.
- **Density** counts water vapour (wetPf2 `Vp`) with its own gas constant: rho = (p - e)/(R_d T) + e/(R_v T).
- **atmPrf `Temp` and `Pres` are dry quantities** (dry temperature and dry pressure, as the files' own `long_name` says). They are now labelled so everywhere, and a composite over a selection containing both atmPrf and wetPf2 no longer averages dry and moist temperature together: each group is split by quantity. netCDF exports record each profile's product and say which rows hold which quantity.
- **WMO tropopause on atmPrf dry temperature**: in moist tropical air the dry temperature's lapse rate falls below 2 K/km near 6 km (450-500 hPa), so 220 of 570 real COSMIC-2 profiles (2026-06-20 and 2026-09-30) were given a tropopause there, up to 12 km below CDAAC's own `trhwmo`. On dry temperature the search now skips levels warmer than 235 K; 568 of 570 then agree with `trhwmo` within 0.3 km (CDAAC's tropopause temperatures never exceeded 233.7 K). wetPf2's moist temperature is searched without the guard, and the `method` field says when it applied.
- **WMO tropopause** accepts lapse rates of exactly 2 K/km ("2 K/km or less") and requires the full 2 km test layer below the search ceiling.
- **Interpolation in log space** for pressure, density, vapour pressure, specific humidity and electron density when profiles are put on a common grid (composites, grid CSV, netCDF). Linear interpolation overestimates these between levels (about 1 % across a 2 km gap in pressure).
- **Profile error bars** ("Rolling Std Dev", "Standard Error") now measure the scatter of the values about their running mean. They were the raw rolling standard deviation, which on a smooth profile measures the vertical gradient: a noise-free straight line got error bars equal to its slope.
- **Composites** grouped by date work (every profile used to land in "unknown"); a group with one profile has undefined (NaN) spread instead of zero.
- **Local times**: ivmL2m `local_time` is local solar time of the first sample (it was the median *magnetic* local time); a per-sample solar local time `slt` is available as a derived field. scnLv2 records without an S4 maximum fall back to the ray start position and its local time.
- **Fill values**: each variable's own `_FillValue`/`missing_value` is masked and `scale_factor`/`add_offset` applied for both netCDF backends; the float32 netCDF default fill (9.96921e36) is now caught. Character variables no longer stop a granule from loading.
- Granule longitudes are normalised to [-180, 180) so the longitude-box search finds products that use 0-360.

### Interface

- Unit strings from the files read unambiguously in titles and CSV headers: refractivity's `N` (which reads as newton) and wetPf2's `N-unit` are "N-units", scnLv2's `unitless` is dropped instead of printed ("S4 index, L1 [unitless]"), and ivmL2m's `N/cc` is "ions/cm³".
- A profile overlay holding atmPrf and wetPf2 `Temp` together was titled "Temperature", although the atmPrf lines are the dry temperature. The title now names each: "Dry temperature (atmPrf); Temperature (wetPf2) [°C]" (found by a browser sweep over real files of every product).
- The relationship scatter says how many occultations it draws twice, as their atmPrf (dry temperature) and their wetPf2 point, when both files of an occultation are selected.
- Groups of an average are drawn in a fixed order (latitude bands south to north, other groups by name) instead of by size, so a group keeps its colour and its place in the key when the counts change between runs.
- The diagnostics panel of a scintillation file (Profiles tab) also gives the tangent height of the S4 peak, which tells the E region (80-160 km in Dymond 2023) from the F region (200-600 km), with a note that a low height can also come from F-region irregularities along the ray, and says that the file's position is the tangent point of the S4 maximum. Checked in the browser at 1024 and 1366 px (a 2026-09-30 file: peak S4 0.51 at 78.4 km).
- Very large and very small numbers in tables, captions and the diagnostics panel are written with a superscript power of ten (4.12×10⁻⁴, 1.23×10⁶) instead of "4.12×10^-4": the sampling card's agreement with CDAAC's `profile_bottom_km` read "to 4.12×10^-4 m", and peak electron densities in el/cm³ looked the same way.
- **The radiosonde comparison says when it left stations out, and the limit can be raised.** It reads the station files of at most 200 stations, those with the most occultations nearby, without saying so: for 5000 atmPrf of May-June 2026, 487 stations were within reach and only 200 were read, giving 297 pairs instead of 391, while the caption spoke of "152 of 200 nearby stations". The caption now gives the number within reach whenever the limit cuts, and **Stations (max)** (1-2000; `max_stations` in `POST /api/validation/radiosonde`) sets the limit; it stays at 200 by default because an earlier year's station file holds the whole record and is often tens of MB. Checked in the browser on those 5000 profiles: 297 pairs with the note at 200, 391 pairs from all 487 stations at 600.

### Exports and figures

- In a profile CSV of scintillation files, the `# Units:` line listed one "seconds since <date>" per file for `time`, which counts from each file's own start; it now says that once.
- Profile plots, averages and latitude-height sections of one product title the field as that product holds it: an atmPrf average of potential temperature reads "Potential temperature (from dry temperature) [K]", an echPrf one "... (ECMWF)". The radiosonde card's "Use only my selection" option says it compares the product chosen on the card.
- The regridded CSV and the netCDF export name a field as each product holds it through one rule (`analysis.quantity_label`): atmPrf's fields derived from temperature are marked "(from dry temperature)" and the model profiles "(ECMWF)" or "(NCEP)", so an export mixing atmPrf and wetPf2 potential temperature says which rows are which.
- The metadata CSV wrote list-valued fields (the IVM latitude range) as Python text, `[-24.1, 24.1]`; they are now semicolon-separated numbers, `-24.1;24.1`.
- The netCDF export's height coordinate carries `positive = "up"`, which CF requires for a vertical coordinate that is not pressure; without it CF tools could not tell the direction of the axis.
- Two exports with the same name started within the same second (the time stamp in the file name has one-second resolution) wrote to the same file, and the second replaced the first. The second now gets a `_2` suffix.
- The regridded (wide) CSV named its field without the product, so an atmPrf `Temp` export said "Temperature" for what is the dry temperature. It now names the field as each product stores it, and lists both when products differ ("Dry temperature [°C] in atmPrf; Temperature [°C] in wetPf2"), as the netCDF export already did.
- The profile CSV header has a `# Units:` line giving every column's units (from the files, or the app's vocabulary for derived fields). Unit strings `C` and `mb` now read `°C` and `hPa` in labels, so atmPrf and wetPf2 temperature and pressure share one unit.
- **Profile CSV with several products keeps every value under its own name.** The columns were those of the first profile, so in an export of atmPrf and wetPf2 together the wetPf2 rows put their values under the atmPrf names (geopotential height under `Ref`, temperature under `Azim`). The columns are now every variable met, each profile's values in its own columns and blank where it has none.
- CSV cells and composite JSON are written at full double precision (they were rounded to 6 decimal places, leaving small fields such as N^2 with one or two significant digits).
- netCDF exports use UDUNITS unit strings (`degree_Celsius`, `kg m-3`, `s-2`, ...). `C` is the coulomb to UDUNITS, so tools that decode units read temperature as a charge.
- The `Software License` line in CSV headers is plain text (name, copyright, URL); it was a Python dictionary dump.
- Export provenance now states that the Profiles-tab outlier/smoothing/uncertainty settings were not applied to the exported values.
- The exported "Group averages" figure reproduces the Compare tab's average: its quantity, height, top and step. It used the Export tab's quantity, the Profiles tab's height and a fixed 0-60 km grid, so an ionospheric composite came out empty.

### Performance

- The CPU worker pool is started in the background when the app opens and when the worker setting changes. Workers are spawned on Windows and macOS and each one imports numpy, scipy and netCDF4, so the first composite or plot after launch used to wait 1-4 s for them: a 200-profile atmPrf composite went from 1.4 s for the first run to 0.3 s.
- New **CPU workers** setting (Settings > Performance) and `--workers N` option for `cosmic2-explorer` and `cosmic2-explorer-server`: composites, profile plots, the diagnostics table, regridded CSV/netCDF exports, importing files and "Rebuild index" read granules on up to N processes when a job has 24 or more granules. 0 = automatic (CPUs - 1), 1 = serial. Results are identical to a serial run. A 400-profile atmPrf composite on 8 CPUs: 21 s serial, 2.6 s with a cold pool, 1.2 s warm.
- Composites and profile plots of a quantity stored in the file (Temp, Pres, ELEC_dens, ...) no longer compute every derived field for each granule: about 25 % less work per profile.
- **Draw** on the Profiles tab reads and filters the selected granules on the CPU workers when 24 or more are selected: 200 atmPrf profiles take about 0.8 s instead of 2.1 s (8 CPUs, pool already running; this includes faster conversion of the arrays to JSON, which also speeds up every other response carrying profile data).
- netCDF-3 granules (all CDAAC products) are read with scipy first: a day-long ivmL2m file loads in about 0.2 s instead of 1.3 s; atmPrf/wetPf2 loads are several times faster.
- The day manifest lists collections and fetches file sizes concurrently.

### Downloads, index and settings

- **The index follows reader fixes by itself.** An index written by an older version is re-read once at start-up, as a background job ("Update the index for this version"), so corrected positions, local times and archive values reach profiles downloaded or imported earlier without **Rebuild index**. Imported files outside the cache folder are refreshed too, which **Rebuild index** never did; each row keeps its stream, level and archive day.
- **A range of days in one go.** The Get data tab fetched one product for one day; statistics over several whole days meant changing the date and fetching again for each day. An optional **Through** date now makes Fetch queue the same product, count and sampling for every day of the range (at most 31; `date_end` in `POST /api/download`, which answers with one job per day), and the whole-day warning gives the size of the range. Checked in the browser with a fresh data folder: scnLv2 for 2026-06-19 through 06-21 gave three completed downloads and three datasets of 24 profiles; a test covers the days across a month end, a range ending before it starts, more than 31 days and unchanged single-day answers.
- **Scintillation files name their satellite like every other product (C2E1-C2E6).** scnLv2 files were indexed as LEO001-LEO006, so the satellite filter listed every COSMIC-2 satellite twice, C2E5 found no scintillation files, and the mission captions did not count them as COSMIC-2. LEO n is COSMIC-2 FM n: on 2025-12-21 and 2026-06-19 each scnLv2 file was matched, without assuming any pairing, to the ionPrf of the same transmitter and time whose tangent point at the S4-maximum height lay within 50 km, and every match was the same satellite (LEO001 with C2E1 17 times, LEO002/C2E2 89, LEO004/C2E4 92, LEO005/C2E5 83, LEO006/C2E6 84; median 8.4 km apart). Files indexed before this version keep their LEO name until **Rebuild index** (Get data); until then they still count as COSMIC-2. Checked in the browser: after the rebuild the filter lists C2E1, C2E2, C2E4, C2E5 and C2E6 only, and C2E5 finds both its scnLv2 and ionPrf files.
- **Other radio occultation missions can be downloaded**: PAZ and KOMPSAT-5 near-real-time profiles, which CDAAC processes into the same atmPrf, wetPf2, echPrf and avnPrf files, through two new streams on the Get data tab (`paz-nrt`, `kompsat5-nrt`; archive `gnss-ro/paz/nrt/...` and `gnss-ro/kompsat5/nrt/...`). The stream code carries the mission, so their files have their own cache folder, dataset key and index stream: deleting a PAZ day removed exactly its 223 granules and left the COSMIC-2 granules of the same product and day in place (checked). "Show what is available" lists another mission only when its stream is chosen, so a COSMIC-2 day scan is unchanged. Whole days of both missions for 2026-06-20 and 2026-09-30 were downloaded and indexed through the API (PAZ 210-223, KOMPSAT-5 78-85 occultations a day; their files already parse, satellite codes PAZ1 and KOM5).
- Granules received before a cancelled or failed download are indexed (the dataset is marked incomplete); they used to stay on disk, unindexed.
- A missing archive directory (for example today's, before CDAAC publishes) is re-checked after 5 minutes instead of being cached for 6 hours.
- The Explore tab's default date range now includes granules observed in the last seconds of the previous UTC day. Every CDAAC day file starts with a few of these (5 of 460 atmPrf on 2026-06-20), and every ivmL2m day file starts at about 23:59:50, so with a single day downloaded its ivmL2m files never appeared in a search.
- "Rebuild index" keeps each granule's archive day (from its cache folder). It used the observation date instead, which moved the granules observed just before midnight to the previous day: deleting that day's dataset then left them on disk and in the index, and grouping by date split them off.
- Re-indexing refreshes the quality code, satellite, PRN and stamp of existing entries.
- "Spread over 24 h" sampling no longer drops ivmL2m files: the `01` in their names is a file sequence, not an hour, so every satellite's whole-day file counted against the same hour (with 24 profiles requested, only one satellite of five was kept). Whole-day products are exempt from the hourly quota.
- A change to "concurrent downloads" takes effect for the next download instead of after a restart.
- The Settings drawer's Save button works again (the DPI field's min/step made the browser refuse to submit the form). The default stream, "require good QC", temperature units and export grid settings are now saved and applied.
- The Profiles tab's diagnostics panel warns when an ionPrf profile has no F2 peak (its largest density is on the top or bottom level, as on profiles cut off below the peak) instead of presenting that maximum as NmF2/hmF2.
- The diagnostics panel follows the selection when the chosen quantity is missing from it (it went on showing a profile from the previous selection, for example an ionPrf profile after selecting scnLv2 records).
- The Profiles tab's diagnostics panel no longer ends in a script error.

### Robustness and security

- The tropopause table and the diagnostic map count each occultation once through one shared rule (`climatology.once_per_occultation`: the wetPf2's value, else the atmPrf's).
- One `analysis.column_stats` (mean, median, spread, count and 95 % interval by level) replaces four identical copies in the weather-model, mission and atmPrf-wetPf2 comparisons; unused imports removed.
- Removed code nothing used: `selectionRequest` in the frontend's api.js, `Granule.to_columns`, `Granule.series`, `DownloadManager.active_count`, and `analysis.solar_local_time`, which duplicated the readers' local-time helper.
- **A cut-off netCDF file is refused instead of read as zeros.** When scipy could not read a classic netCDF file, the reader fell back to netCDF4, which opens a truncated file and returns zeros for the missing records: a partly downloaded ivmL2m was indexed at 1970-01-01 00:00 UTC with local time 0 and 24902 zero densities. A classic netCDF file that scipy cannot read is now reported as unreadable (truncated?); netCDF-4 files still go to netCDF4.
- Removed `exporters.export_bundle` (a ZIP of several exports), which no endpoint or page called; the README no longer lists a ZIP export.
- Removed three functions nothing called: `analysis.anomaly_against`, `catalog.readable_products` and `plotting.check_layout` (its docstring named a test that no longer used it).
- The local API accepts cross-origin requests only from loopback origins; previously any web page open in the browser could call it (including the delete endpoints).
- Grid, DPI and settings values are validated (a zero grid step returned a server error, and could be saved as a setting).
- The coverage summary (the Explore overview and the "Sampling summary" figure) no longer needs SQLite's optional `FLOOR` function, which is absent from SQLite builds without math functions (for example the system SQLite 3.34 of RHEL/Rocky 9).
- The test suite removes its temporary data folder when it finishes.
- A browser test (`tests/test_browser.py`, Playwright with Chromium, skipped when not installed) loads the bundled samples and goes through every tab and main action, failing on any script error or error message.
